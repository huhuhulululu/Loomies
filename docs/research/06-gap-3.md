# 06 · Gap-3 架构裁决：「无自建后端（纯端侧+直连 API）」 vs 「轻后端」

> 调研日期：2026-07-21。检索受限说明：本 session WebSearch 配额耗尽、exa key 失效，全部证据来自 WebFetch 直连一手来源（官方文档 / GitHub / HuggingFace / 定价页），URL 均可核查。

## TL;DR 裁决

**两条路线都不选原教旨版本，裁决为「端侧优先 + 无状态 AI 代理」混合架构**：

- 感知层（衣物 embedding、以图搜衣、相似检索）**端侧跑**——CLIP 类模型 Core ML 化已被 Queryable / Apple MobileCLIP 官方工件充分验证，百件级检索暴力余弦即可；
- 数据层（衣橱库、搭配收藏、标签、体型数据）**CloudKit 私有库**——零服务器、零账号注册摩擦、隐私叙事完整；
- 智能层（VLM 细粒度打标、LLM 搭配生成）**必须出网**，而「客户端安全直连云 API」在密码学上不成立（密钥必可被提取；App Attest 本身就要求你有服务器做验证）→ 最低配是**一个无状态密钥代理**（Cloudflare Workers $0–5/月 + App Attest/App Check），或直接用 **Firebase AI Logic**（Google 托管代理，零自维护）；
- **不上** Supabase/Fly.io 式全功能后端，**不做**自建账号体系（MVP 阶段）。
- 单位经济：用 Gemini Flash-Lite 级模型，300 件入库打标一次性 ≈ $0.1–0.3，搭配生成 ≈ $0.003/次，**每免费用户月成本可压在 $0.5 以内**，免费层完全可行。

## 1. 端侧能力边界：实测证据

### 1.1 CLIP 类模型 Core ML 端侧推理（已验证的先例）

**Queryable**（开源 iOS 相册语义搜索，把 OpenAI CLIP ViT-B/32 转 Core ML 端侧跑）：

- Text+Image Encoder 合计约 **300MB**（≈fp16）；
- 索引吞吐：**iPhone 12 mini 上约 2000 张/分钟**（≈30ms/张，含解码）；
- 检索：**1 万张以内 <1s，3.5 万张约 2.8s**（暴力相似度）；最低支持 iPhone 11 / A13；
- 2024-09 起默认模型换成 Apple **MobileCLIP-S2**。
- 来源：<https://github.com/mazzzystar/Queryable>；博客实测 <http://mazzzystar.com/2022/12/29/Run-CLIP-on-iPhone-to-Search-Photos/>

**Apple MobileCLIP 官方数据**（iPhone 12 Pro Max 实测，image + text encoder）：

| 变体 | 参数(M, img+txt) | 时延(ms, img+txt) | IN-1k 零样本 |
|---|---|---|---|
| S0 | 11.4 + 42.4 | **1.5 + 1.6** | 67.8% |
| S2 | 35.7 + 63.4 | **3.6 + 3.3** | 74.4% |
| B  | 86.3 + 63.4 | **10.4 + 3.3** | 76.8% |

- 官方仓库含 iOS demo app；官方 **Core ML 导出工件已在 HF 发布**（S0/S1/S2/B/B-LT，text+image 双编码器齐全）。S0 零样本≈OpenAI ViT-B/16 但快 4.8×、小 2.8×。
- 来源：<https://github.com/apple/ml-mobileclip>；<https://huggingface.co/apple/coreml-mobileclip>

**外推到 iPhone 15/16**：上表在 A14（iPhone 12 代）测得；iPhone 15（A16）/ iPhone 15 Pro 与 16 系（A17 Pro/A18，Neural Engine 标称 35 TOPS vs A14 的 11 TOPS，公开芯片规格）只会更快。**结论：单图 embedding 在现代 iPhone 上是个位数到十几 ms 的问题，300 件衣橱全量重建索引 <1 分钟，非瓶颈**。内存上 ViT-B 级 fp16 权重 ≈200–300MB，配合 coremltools 量化（6-bit palettization 等）可再压；iPhone 15 Pro 起 8GB RAM，加载单编码器无压力（推断，非实测）。

### 1.2 FashionCLIP / Marqo-FashionSigLIP 的端侧化现状

- **FashionCLIP 2.0**：ViT-B/32 底座、0.2B 参数、MIT 许可、Farfetch 80 万商品对训练；提供 **ONNX** 导出，**无官方 Core ML**。来源：<https://huggingface.co/patrickjohncyh/fashion-clip>
- **Marqo-FashionSigLIP**：ViT-B-16-SigLIP 底座、0.2B 参数（F32）、Apache-2.0；对 FashionCLIP 检索指标 **MRR/召回最高 +57%**（T2I MRR 0.239 vs 0.165）；**无官方 ONNX/Core ML 导出**。来源：<https://huggingface.co/Marqo/marqo-fashionSigLIP>
- 两者均为 ViT-B 级（与 MobileCLIP-B 同量级：86M 图像编码器，iPhone 12 Pro Max 10.4ms），**Core ML 转换在架构上无根本障碍**（标准 ViT/文本 Transformer，coremltools 支持 PyTorch 转换：<https://apple.github.io/coremltools/docs-guides/source/convert-pytorch.html>），但**需要自己做转换+量化+ANE 适配验证，属 1–2 周级工程而非现成品**。
- **务实路径**：MVP 直接用 Apple 官方 coreml-mobileclip（零转换成本、有官方时延背书），时尚域检索精度不够时再自转 FashionSigLIP。衣橱内检索是「几百件闭集」而非「百万商品开放集」，通用 CLIP 的域差损失被大幅稀释（推断）。

### 1.3 百件级端侧向量检索：暴力余弦即可

- **量级判断**：100–300 件 × 512–768 维 fp16 ≈ 仅 0.1–0.5MB 数据。Queryable 用暴力检索 1 万向量 <1s（上文实测），300 向量在任何 iPhone 上都是亚毫秒–毫秒级（Accelerate/vDSP 点积）。
- **sqlite-vec**：纯 C、可在 iOS 编译（作者发布说明明确「Android、也能在 iOS 编译」）；**暴力扫描**架构，实测 SIFT1M（100 万×128 维）17–33ms/查询，10 万级 float 向量 <75ms；ANN 在路线图上。pre-v1，有破坏性变更风险。来源：<https://github.com/asg017/sqlite-vec>；<https://alexgarcia.xyz/blog/2024/sqlite-vec-stable-release/index.html>
- **ObjectBox**：HNSW ANN，**官方支持 Swift**，磁盘+缓存不受内存限制；但面向十万–百万级向量的场景。来源：<https://docs.objectbox.io/on-device-vector-search.md>
- **结论：百件级用 SQLite/Core Data 存 blob + 内存暴力余弦即可，sqlite-vec/ObjectBox 都是过度工程**；到「万级向量」（如逐 patch 检索或全量搭配历史）才考虑 sqlite-vec。

### 1.4 outfit-transformer 兼容性打分端侧化评估

- 现状：**非官方 PyTorch 实现**（官方未开源），CLIP embedding 背骨 + Transformer 编码器；Polyvore 数据集上 CP AUC 0.95 / FITB 69.24；MIT，提供预训练 checkpoint（Google Drive）。来源：<https://github.com/owj0421/outfit-transformer>
- Core ML 化技术可行性：**中等**——标准 Transformer 编码器结构可转（复用 1.1 的结论），且背骨与端侧 CLIP 可共享。
- 但 MVP 风险高：(a) 非官方实现+外链权重的供应链质量；(b) **Polyvore（电商白底图、欧美搭配惯例）→ 用户实拍衣橱的域差未验证**；(c) 兼容性分数是标量，难以直接支撑「为什么这么搭」的可解释推荐文案——后者恰是 LLM 强项。
- **结论：不作为 MVP 依赖**。MVP 用「端侧 embedding 粗筛（颜色/品类/相似度启发式）+ 云 LLM 精排与生成文案」；outfit-transformer 作为 P2 期端侧化候选（省云端搭配调用成本时再评估）。

## 2. 无自建后端时，客户端直连云 VLM/LLM 的密钥安全

### 2.1 基本事实：客户端内嵌 API key 不可行

App 二进制/网络层中的密钥必可被提取（越狱抓包、静态分析），OpenAI/Google 均按 key 计费无设备级配额——泄漏即刷爆账单。此为行业共识，无需逐条溯源。

### 2.2 App Attest：有效，但它本身就意味着「你有服务器」

Apple 官方流程：设备 Secure Enclave 生成密钥 → 向 Apple 认证（attestation）→ 之后每个敏感请求带 assertion；**「不能依赖 app 自身逻辑做安全检查……attestation/assertion 必须由你自己的服务器验证」**（含 challenge 防重放、keyId 持久化、失败处置策略）。来源：<https://developer.apple.com/documentation/devicecheck/establishing-your-app-s-integrity>

→ **推论（本裁决的关键逻辑）**：所谓「无后端 + App Attest 保护直连」是伪命题——App Attest 的验证方就是一个后端。最小形态是**无状态验证代理**：Cloudflare Worker 收 assertion → 验签 → 转发 LLM 请求（注入服务端密钥）→ 回传。无数据库、无账号，免费档 10 万请求/天或 $5/月（见 §3）。局限：App Attest 不覆盖全部滥用向量（合法设备上的高频调用仍需服务端限频），密钥不随备份迁移需重新 attest。

### 2.3 托管代理：Firebase AI Logic（最省事的「准无后端」）

- 官方定位：客户端 SDK（**含 Swift**）经 Google **代理网关**调 Gemini，**API key 不进 app**；集成 **Firebase App Check**（Apple 平台用 App Attest/DeviceCheck 做 attestation）防未授权客户端，默认开启**每用户限频**且可配置。
- App Check 官方局限声明：「阻止部分而非全部滥用向量，不保证消除所有滥用」；也可保护自有后端。
- 计费：走 Gemini Developer API（含免费层）或 Vertex AI；模型侧按 Gemini 标准价（§4）。
- 来源：<https://firebase.google.com/docs/ai-logic>；<https://firebase.google.com/docs/app-check>
- 权衡：省掉自建代理的运维，但引入 Google SDK 依赖、且锁定 Gemini 系模型（对本 App 够用，打标/搭配 Flash-Lite 级即可）。

### 2.4 澄清：「CloudKit Functions」不存在

CloudKit 提供的是**数据库/同步/存储**（私有库计入用户 iCloud 配额、公共库最高 1PB 免费额度），**无服务器端自定义函数/计算能力**——不能在 CloudKit 里藏密钥做转发。来源：<https://developer.apple.com/icloud/cloudkit/>。CloudKit 在本架构中的正确角色是**数据平面**（衣橱/搭配/标签/体型数据私有库同步），而非 AI 代理。

## 3. 若上轻后端：最小配置月成本 + 账号摩擦

|---|---|---|---|

**账号体系的转化摩擦**：Baymard 汇总研究（2006–2025，近 50 项研究）电商弃购率均值 70.22%，其中 **18% 的弃购原因是「网站要求我创建账号」**（仅次于额外费用 40%）。来源：<https://baymard.com/lists/cart-abandonment-rate>。虽为电商结账数据，方向性结论可迁移：**MVP 不应把注册置于核心价值（扫衣入库）之前**。iOS 上的零摩擦替代：CloudKit 以 Apple ID 为隐式身份（无注册流程）；若走 Supabase 则用匿名登录+后置绑定。**百件级向量检索在端侧已解决（§1.3），服务端向量库（Vectorize/pgvector）在 MVP 阶段无必要**——这是「轻后端」不需要长成「全后端」的核心理由。

注：**题目点名的 GPT-4o mini 已从 OpenAI 当前价目页移除（legacy）**，且其图像走「base+tile 高倍率」token 法（一张 1024² 高清图 ≈2.5 万 token 量级，官方 vision 指南 <https://developers.openai.com/api/docs/guides/images-vision>），早已不是打标性价比选项；现役等价档是 gpt-5.4-nano/mini。Gemini 图像 token 规则：**双边 ≤384px 记 258 token；更大按 768×768 tile 每片 258 token**（1024² ≈ 4 tile ≈ 1032 token）。来源：<https://ai.google.dev/gemini-api/docs/image-understanding>

### 4.2 单件打标成本（1024² 图 + ~200 token 提示词 + ~250 token 结构化标签输出）

- Gemini 3.5 Flash-Lite：输入 ~1250 tok×$0.30/M + 输出 250×$2.50/M ≈ **$0.001/件**（图片压到 ≤384px 或走 Batch 半价 → ~$0.0005）
- gpt-5.4-nano：≈ **$0.0008–0.001/件**（同量级）
- **人均入库成本（一次性）**：100 件 ≈ $0.1；**300 件 ≈ $0.3**（Batch/降分辨率后 ≈ $0.15）

### 4.3 搭配生成成本（文本为主：衣橱标签清单 ~3k tok 输入 + ~700 tok 输出）

- Flash-Lite：≈ **$0.003/次**；gpt-5.4-mini（要更强推理/文案）≈ $0.005–0.006/次
- 若每次附 4–6 张单品图（≤384px，258 tok/张）：+ ~1–1.5k tok ≈ +$0.0005/次，可忽略
- 日 3 次 × 30 天 = 90 次/月 ≈ **$0.3/月（Flash-Lite）～ $0.5/月（gpt-5.4-mini）**

### 4.4 每免费用户月成本上限与额度反推

- **稳态**：$0.3–0.5/月（搭配为主）+ 增量入库零头；**首月**（含 300 件全量入库）≈ $0.6–0.8。取安全系数 ×2（重打标、失败重试、长输出）→ **上限 ≈ $1–1.5/首月，$0.5–1/稳态**。
- **免费额度设计建议**：免费层「入库 100 件 + 搭配 1–2 次/日」→ 摊到 **<$0.2/月/免费用户**，1 万免费 MAU 的模型账单 <$2000/月上限、实际（活跃度衰减后）大概率数百刀；付费层解锁无限入库+高频搭配+强模型（3.5 Flash/5.4-mini 精排）。代理侧成本几乎为零（§3）。Gemini Developer API 免费层还可承接开发/内测流量（<https://ai.google.dev/gemini-api/docs/pricing>）。

## 5. 裁决与「on-device 隐私」叙事影响

### 5.1 裁决：端侧优先 + 无状态 AI 代理（二选一实现：自建 Worker 代理 / Firebase AI Logic）

1. **端侧**：MobileCLIP(S2 或 B) Core ML 做 embedding；内存暴力余弦做检索；CloudKit 私有库做数据同步；体型 avatar 端侧渲染。→「无自建后端」路线中**成立的部分全部保留**。
2. **出网**：细粒度打标（VLM）与搭配生成（LLM）走代理调 Flash-Lite 级模型。→「无自建后端」路线中**不成立的部分（密钥安全）用最小代价补齐**：Cloudflare Worker（$0–5/月）+ App Attest 验证，或 Firebase AI Logic 托管（零运维，锁 Gemini）。
3. **不做**（MVP）：自建账号体系、服务端向量库、Supabase/Fly 全后端、outfit-transformer 端侧化。升级触发器：需要 Android/Web 端或社区功能 → 届时上 Supabase（匿名登录后置绑定）；云搭配调用成本占比过高 → 评估 outfit-transformer 端侧化替代 LLM 精排。

### 5.2 对「on-device 隐私」差异化叙事的影响

- **叙事需从「100% 端侧」降级为「端侧优先（on-device first）」，但仍然成立且可验证**：衣橱数据库、向量索引、体型数据全部留在设备与用户本人 iCloud 私有库（Apple 管理密钥，开发者不可读）；**没有开发者可访问的用户数据库存在**——这是对 Supabase 路线的真实差异点，不是营销话术。
- **诚实披露口径**：仅当用户主动请求 AI 打标/搭配时，该请求所需的图片/标签**瞬态**经代理送往模型 API，不落库。付费档 Gemini API 明示「内容不用于改进产品」，**免费档会被用于产品改进**（<https://ai.google.dev/gemini-api/docs/pricing>）→ **生产流量必须走付费档**，否则隐私叙事直接破产；App Privacy 标签需申报「照片-与用户关联-App 功能」。
- **可选的叙事强化**（P2）：提供「纯端侧模式」开关（只用 embedding 启发式搭配、无云调用），把隐私从声明变成产品功能；待 Apple Foundation Models / 端侧小模型成熟后逐步回迁打标任务。
