## 1. 产品定位

**一句话**：面向职业女性的多场合数字衣橱——扫描入库、按场合与天气推荐搭配、管到「哪件衣服在哪个柜子的哪个抽屉」。

**已裁决**：首发**美国区**（en-US 主语言、英制单位优先可切公制、US 尺码优先展示、合规主口径 = 美国）；中国区合规链（ICP/网信办登记/国产模型）后置到进入中国市场时启动（预案见 `06-gap-1.md`）。

### 1.1 目标用户

- 主画像：25-45 岁美国职业女性，工作日通勤/会议、周末社交/约会、周期性差旅，多场合切换频繁
- 次画像：多地生活者（两地衣柜）、为家人（孩子）管理衣橱的母亲（已裁决：孩子档案不进 MVP，v2 携完整合规方案再上）
- 付费敏感点（调研实证）：订阅陷阱是本品类最大口碑雷区（约 34% 差评涉付费墙，Style DNA 因此口碑崩塌）；Stylebook $4.99 买断被反复表扬
- **适用范围声明**（R13 已裁决：隐式开关，不加人群字段）：产品为女性优先设计，但不设性别门槛——FFIT 体型判定/体型加权/纸娃娃/合身标记是**成年女性专属公式**，以「用户是否已录入完整身体维度（胸/腰/臀/上臀）」作激活开关：录满即进合身体验，未录则整簇隐藏（其余功能全可用）；首次激活弹一次性说明「这些合身功能基于女性身材比例」；App Store 描述如实声明「designed for women's wardrobes」。反悔成本低——若上线数据显示非目标用户混淆，再加可选 audience 字段（加法演进，冻结例外允许）

### 1.2 竞品格局与空白（`01-competitors.md`）

| 阵营 | 代表 | 启示 |
|------|------|------|
| 老牌工具 | Stylebook（$4.99 买断，iOS 独占 15 年） | 单平台深耕工具型商业上可持续 |
| 社交头部 | Whering（1000 万用户，2026-07 获 eBay/Google $7M） | 录入摩擦与性能是其最大差评源 |
| 免费+人工服务 | Indyx（数字化免费，造型服务变现） | 大方免费层是口碑资产 |
| AI 新贵 | Alta（$11M）、Doji（$14M）、Google Doppl | 照片 avatar 试穿门槛已被拉低，均押注购物佣金，**不做衣橱管理深度** |
| 中文市场 | 搭搭（200 万用户）、尽简衣橱 | 存放位置/换季收纳需求已被验证，欧美近空白 |

**四个市场空白（定位依据，已经 MARKET.md 需求侧验证并修正）**：
1. 职业女性多场合定位——修正：Alta 已部分占据场合叙事，真空白是「场合结构化硬过滤 + 推荐正确性」（竞品执行集体失败）
2. 「身体维度 → 合身判断」无人做成（Style DNA 收测量而不用）——定位从可视化转向合身判断（H3 GO-重定位）
3. 存放位置/换季——**降级为留存钩子 + 整理师渠道抓手**，不作获客卖点（行为普遍但显性 App 需求弱，H2 GO-降级）
4. 不卡件数 = 入场券（头部已免费无限）；隐私 = 信任设计非获客钩子；升级两个可营销差异：「没有可以宕机的服务器」（Smart Closet 死亡实证）+「克制的 AI」（接反 AI-slop 情绪）

防御策略 = **合订本**：推荐卡片同屏呈现 合身标记 + 存放位置 + 场合——单点可抄、组合难抄（MARKET.md §7 护城河排序）。

## 2. 数据模型（分层多衣柜架构）

> ✅ **本章四条派生语义已经用户确认（2026-07-21，R10 裁决）**：① Person/Wardrobe 拆层（身体档案跟人走）；② 单品「可转移不可共属」及缺件置灰语义；③ 天气按衣柜所在地取；④ 搭配不跨柜但检索跨柜。
> **数据模型自此冻结**，后续变更需重新裁决。
> 冻结例外条款（§11.1）：**加法式 schema 演进不算破冻**（新增 optional 字段/新实体，CloudKit 迁移约束所需）；改语义/删字段/改关系才需重新裁决。

### 2.1 层级结构

```
账户（iCloud，零注册——Apple ID 隐式身份）
└── Person 人物档案            ← 身体维度/体型跟「人」走（已确认）
    └── Wardrobe 衣柜          ← 隔离边界（泰国的衣柜/纽约的衣柜/孩子的衣柜）
        ├── StorageLocation    ← 存放位置树（柜 → 区 → 抽屉/收纳箱）
        ├── Item 单品          ← 唯一归属一个衣柜，可「转移」不可「共属」（已确认）
        └── Outfit 搭配        ← 硬约束：只引用本衣柜内的 Item（已确认）
```

### 2.2 核心实体

**Person**
- 身体维度：身高、体重、胸围、腰围、臀围、上臀围（FFIT 判定必需）、肩宽、内长等，全部可选渐进补全；单位英制优先（in/lb）可切公制
- 体型：FFIT 2020 修正版判定（9 类，UI 折叠为大众 5 类），纯函数本地计算（`04-body-avatar.md`）；**激活门（R13）**：仅当胸/腰/臀/上臀四维度录满才计算并展示，未录满则 FFIT 簇（体型判定/加权/合身标记/纸娃娃）整体隐藏
- 个人色彩季型（12 季型，作推荐加权项；R11 已确认保留，录入可选）
- 偏好：怕冷/怕热偏置、禁忌项、特殊需求自由文本
- 隐私：**身体维度默认仅本地存储域（不进 CloudKit 同步）**——Codex 审计发现的口径冲突：若按 Health 类目申报，5.1.3 禁止个人健康信息存 iCloud；仅本地化同时消除该风险与「体型档案跨设备」的敏感面（代价：换机需重录几项维度，可接受）。不接 HealthKit，不用于广告，采集时**单独同意弹窗**；分类口径（是否按 Health 申报）列法务确认项
- **出网不变量：身体维度与体型分类永不出网**——体型/合身加权全部在端侧预筛完成，云端 LLM payload 仅含单品标签与场合/天气上下文（这是市场空白 #4 隐私叙事的支点，违反即叙事塌方）

**Wardrobe**
- 归属人（Person）、所在地（城市 → 决定 WeatherKit 天气源，已确认）、名称、封面

**StorageLocation**（树形）
- 类型：挂杆/层板/抽屉/收纳箱/换季箱；可挂照片
- 主路径是逻辑格位树标签；RoomPlan「衣柜地图」仅作 Pro 机型柜级可视化增强（`08-lidar-3d-scan.md`：RoomPlan 只给外包围盒，不识别柜内隔层）

**Item**
- 图像：原图 + 抠图 + 缩略图（`@Attribute(.externalStorage)` → CKAsset）
- 分类/属性：以 Fashionpedia 本体（46 类目 + 294 属性，CC BY 4.0）为 schema 起点，扩展用户自定义标签
- **场合标签**（多选：business formal / business casual / 通勤 / 约会 / 宴会 / 休闲）——F4 硬过滤依赖
- **适穿温区/保暖度**：由类目 + 材质推导默认值、用户可改——F4 硬过滤依赖；Outfit 适穿温区由成员单品聚合得出
- **护理**（结构化：只干洗/手洗/不可烘干等，可由洗标 OCR 填充）
- **尺码双层分离**（`07-sizing-entry.md`——尺码跨品牌不可比已实锤）：
  - `nominalSize`：尺码体系枚举（US 优先/EU/UK/JP/CN_GBT/INTL）+ 原始标签字符串保真
  - `measurements`：品类化平铺实测（上装：胸宽/衣长/肩宽/袖长；裤：腰宽/臀宽/内长……借用二手平台事实标准字段集），每字段带溯源标记（实测/推断/未填），默认可留空
- 状态机：可用 / 在洗 / 干洗中 / 外借 / 闲置 / 待处理——推荐引擎只取「可用」
- 备注：自由文本特殊需求（「需配腰带」「易皱」）
- 端侧 embedding 向量（语义检索与搭配打分用，排期见 §7 v1.x）+ **modelVersion 元数据**（换模型后按版本判废、后台分批重算——限充电/夜间，迁移期回退属性检索）
- 转移历史

**Outfit**
- 不变量：`outfit.items ⊆ outfit.wardrobe.items`（创建与推荐时强制）
- 字段：场合、适穿温区（成员聚合）、拼贴布局 + 纸娃娃布局、来源（AI/手动）、AI 推荐理由、收藏、状态（完整/缺件）

**WearRecord / CalendarPlan**
- 穿着记录：一键打卡「今天穿了这套」+ 可选合身反馈（紧/合/松）；**记录时固化衣柜快照**（单品日后转移不改历史统计口径）
- 日历计划：日期 × 衣柜 × 搭配

### 2.3 跨衣柜语义 + 级联语义

**跨衣柜操作矩阵**：

| 操作 | 是否跨衣柜 |
|------|-----------|
| 搭配（推荐/手动） | ❌ 硬禁止（用户硬约束） |
| 查找/盘点（「蓝衬衫在哪」） | ✅ 全局检索（已确认） |
| 单品转移/批量打包 | ✅（转移即改归属，历史留痕） |
| 统计（利用率/花费） | ✅ 可按衣柜/按人聚合 |

**转移级联表**：

| 波及对象 | 语义 |
|---------|------|
| 原衣柜内含该单品的 Outfit | 标记「缺件」置灰不删除；单品转回自动恢复 |
| 引用缺件搭配的 CalendarPlan | 标记「待处理」并通知用户改计划 |
| WearRecord / 统计 | 不受影响（记录时衣柜快照已固化） |
| 差旅打包 | 定义为**临时转移**（区别于永久转移），行程结束「一键回迁」批量恢复 |

**删除语义表**：

| 删除对象 | 级联规则 |
|---------|---------|
| Wardrobe | 阻断式：须先批量转移单品，或二次确认整柜级联删（Item/StorageLocation/Outfit/CalendarPlan 一并删，WearRecord 保留） |
| Person | 阻断式：须先处置名下全部衣柜 |
| Item | 含它的 Outfit 标「永久缺件」（与转移缺件区分展示）或由用户选择解散；WearRecord 保留（维护统计完整性） |
| StorageLocation 节点 | 子树上的 Item 位置归属提升至父节点 |

**同步合并协议**（Codex 审计：CloudKit 最终一致性下仅靠「创建时检查」守不住跨柜不变量）：
- 实体带稳定 UUID + revision；删除用 tombstone；转移/回迁为**幂等操作记录**（opID + 时间戳），并发转移按操作时间戳胜出
- **合并后修复器**：每次同步合并完成运行不变量校验——发现跨柜引用的搭配 → 自动标「缺件」并通知；发现孤儿位置引用 → 提升父节点；修复动作幂等可重放
- 双机离线竞态（A 转移 × B 同时用该单品建搭配、并发删除、差旅回迁冲突）列入 §11.2 测试清单

## 3. 功能规格

### F1 扫描入库（生死线功能）

调研实证：录入摩擦是本品类用户评论第一大抱怨点（是否为「第一流失点」无公开数据，作为强设计假设对待）。

流水线（`02-opensource.md` + `03-ios-stack.md`）：
1. **连拍采集**：AVCapturePhotoOutput（fast capture prioritization + deferred processing），支持批量相册导入
2. **端侧抠图**：`VNGenerateForegroundInstanceMaskRequest`（iOS 17+，免费、离线）；多件同框用 SAM2 点选辅助（Apache-2.0，Apple 官方 Core ML 版）；失败兜底服务端 rembg/BiRefNet（MIT）
3. **抠图可手修**（竞品被骂点，必须做）：边缘涂抹修正
4. **AI 预填属性**：云端 VLM 打标，**全部标签可编辑**——实测 category 87-95% 可用；material 通用 VLM 仅 ~43%，默认弱展示；color 默认展示但必须易改（对抗核查记录提示部分基准下 exact-match 精度极低，小样本口径 N=461，`05-recommendation.md` 报告正文未收录该数字——按「可用但必须易改」保守处理）
5. **单屏确认**：滑动确认/修正 → 入库；修正回流为个性化信号

**照片访问策略**：默认 PHPicker 零权限路径（批量多选已覆盖导入场景，不申请全库权限）；仅未来做「相册新增自动提醒入库」类功能才申请库权限并单独解释；隐私标签口径同步。
**打标质量监控**：端侧统计分属性修正率（category/color/material 分开）→ 匿名聚合上报（复用 §11.8 遥测通道）；阈值告警（如 category 修正率 >15%）→ 动作 = 回滚 prompt 版本 / 下调该属性展示档位；修正样本反哺 prompt 回归集（§4.4）。

验收基线：受控拍摄抠图成功率 ≥90%；百件级衣橱列表流畅（竞品普遍工程短板——缩略图管线/懒加载/本地缓存为一级验收标准）。

### F2 尺码与维度录入（差异化卖点）

三层递进（洗标 OCR / 尺码归一化 / 维度级 fit 判断均无竞品覆盖）：
1. **快速层**（⚠️ **v1.0 未接，见 D102**：`makeOCR` 无平台分支、恒返回 mock；
   产品面已如实披露「字段是起点不是识别结果」。端侧 `RecognizeTextRequest` 不需要
   Worker 也不需要配额，是 v1.x 的第一优先）：拍洗标/吊牌 → 端侧 OCR
   （`RecognizeTextRequest` + 品牌 customWords；iOS 26 `RecognizeDocumentsRequest`
   结构化抽取+条码、26 语言）→ 自动填品牌/尺码/成分/护理 → 单屏确认。条码反查仅作辅助（GS1 库无尺码字段）
2. **结构层**：尺码体系字段（v1.0）+ 品牌尺码表映射（v1.x 随种子库启用）。⚠️ 无现成可商用尺码表数据库 → 自建高频品牌种子库 + 众包回填
3. **实测层**（可选）：平铺测量字段（§2.2）；平铺拍照自动测量（Size AI 宣称 5-9mm 精度，厂商自述）列 P2 观察项

**Fit 引擎**（首版确定性、零数据冷启动）：
```
ease（放松量）= 服装周长（2 × 平铺宽）− 身体净围
→ 按品类/版型查阈值带 → 紧 / 合身 / 宽松
```
与商业验证过的 Bold Metrics 同构；穿着反馈逐步个性化阈值；**全程端侧计算**（身体数据不出网不变量）。

### F3 标签与存放位置

- 双层设计：**结构化字段**（存放位置、场合、状态、护理）+ **自由注释**（特殊需求）
- 存放位置树：衣柜 A → 挂区/抽屉 2/换季箱 3；换季批量移位操作
- 全局查找：跨衣柜搜索定位；v1.0 用属性/标签检索，语义检索（自然语言找衣）随 embedding 层上线（v1.x）
- P2：RoomPlan 柜级衣柜地图（`isSupported` 检测降级，数据模型不依赖其输出）

### F4 搭配推荐（三层引擎）

> **核心机制 = copilot（v0.9 PIVOT，用户掌舵）**：方法④证据（约 7:1 倒向规划器；「我选几件→AI 补全」被爱，「给一件就自动成套」被恨到退订）确立主交互为——
> **用户锚定场合 +（可选）几件单品 → 引擎补全成合规搭配、给几个打分候选供用户选**，而非算法替用户决定一套。用户始终在驾驶位。
> **full-auto「直接告诉我穿什么」作可选模式**（服务急性决策疲劳/人生过渡期的高痛子群，方法④证实其真实但小众）。
> 引擎逻辑不变（下表三层全复用），改变的是**输出契约**：从「1 套定论」变为「锚定→补全→候选供选」。每日推送=一个**起点建议**（可接受/微调/重配），非强制。

候选集永远先按 **当前衣柜 + 状态可用 + 场合档位 + 温区** 硬过滤（多衣柜硬约束在此层实现），然后：

| 层 | 机制 | 上线 |
|----|------|------|
| 规则层（兜底，全设备） | 色彩（60-30-10/色轮）、场合四档（映射单品白黑名单）、体型加权（FFIT × 单品属性二维可配置表，端侧）、近期重复防护（数据源 = 穿着打卡；默认硬排除，会清空候选时降级为降权，D89）、个人色彩加权（R11 已确认） | v1.0 |
| Embedding 层 | 端侧 embedding 向量 + 暴力余弦（百件级 <1s，Queryable 实测）+ Loom 式规则打分 | v1.x |
| LLM 编排层 | 端侧预筛候选精简 JSON → 云端 LLM → strict schema 搭配 JSON + item id 白名单校验 → 带理由输出；payload 不含身体数据（§2.2 不变量） | v1.x |

**Outfit 语法与属性置信语义**（Codex 审计 + 需求侧差评清单共同要求）：
- 槽位语法：{上装+下装 | 连衣裙} 为基底，鞋必选，外套按温区条件加层；互斥规则（禁双 blazer、禁双下装）；成套完整性校验（缺下装=非法）
- 三值属性：场合/温区/材质取「已知/未知/低置信」——**未知与低置信不做硬过滤**（否则冷启动空候选），改降权 + 入库确认时补齐；候选覆盖率低于门槛 → 自动切「锚点单品补全」模式
- **四条正确性验收（v1.0 硬门，来自竞品差评实证）**：①天气实时且只按日间时段计算（竞品拿夜间低温推毛衣的差评在案）②场合硬过滤 ③≥7 天防重复（**默认硬门；硬门会清空候选时自动降级为降权并如实告知**，见 D89）+ 在洗/外借状态感知 ④组合语法合法——四条各配自动化测试用例

**双轨降级**：Apple Foundation Models 按 `SystemLanguageModel.availability` 三态降级；FM 上下文当前 4096 token，只做候选内组套、标签归一、短理由；完整推荐走云端。

**每日节奏（copilot 框架）**：按天气（衣柜所在地）× 场合档位 × 体型加权，早推一个**起点建议**（非强制的 1 套定论）——用户可一键接受、微调（换某件）、或从「锚定→补全」重配。**免费层每日推送由端侧规则层生成（零边际成本、不计配额）**；LLM 搭配为用户主动触发、按次计配额；Plus 可升级推送为 LLM 生成。full-auto 模式的用户，推送即当日直接方案。

**冷启动**：衣橱 < 阈值时改「锚点单品补全」（你想穿这件我帮你配）；onboarding 限 3-5 题；可选胶囊模板引导补拍。

**推荐质量评估**：北极星指标 = 推送 → 接受/打卡率，辅以「换一套」率；内部标注离线评测集（~200 套好/坏搭配）；任何层级上线、规则变更、prompt 变更须先过评测集，线上走 A/B 门槛（指标采集依赖 §11.8 遥测）。
**规则资产运营**：FFIT×属性二维表、色彩规则、温区阈值均为**版本化 JSON**——初版由外部造型顾问评审产出，App 内置默认值 + Worker 托管远端覆盖（热更新不走发版）；变更过评测集后灰度下发，保留回滚版本。

### F5 搭配存储与穿搭日历

- 搭配收藏夹：按场合归档、手动拼贴编辑器（仅本衣柜单品可见）——需求原生功能
- 穿着打卡（一键「今天穿了这套」+ 合身反馈）——fit 闭环需求原生
- **「距上次洗涤已穿几次」显性化**：Reddit 用户点名无人做的需求，Item 状态机已覆盖，零成本差异点（MARKET.md）
- 穿搭日历：计划 + 实穿记录
- 统计簇：cost-per-wear、利用率、闲置提醒、季度穿着回顾（竞品验证的留存钩子；R11 已确认）
- 差旅打包模式：选目的地衣柜 + 日期 → 打包清单 → 临时转移 → 一键回迁（R11 已确认）

### F6 体型与着装可视化

调研结论（`06-gap-2.md`）：「真实衣物照片变形贴到风格化剪影」**无成功商业先例**，纯几何 TPS 伪影风险高——不赌这条路。

**双视图（R16-A：v1.0 只做平铺拼贴，纸娃娃降 v1.x）**：
1. **平铺拼贴**（搭配管理主视图，**v1.0**）——市场充分验证
2. **锚点缩放纸娃娃**（体型示意视图，**v1.x**）——身体维度参数化生成单色 croquis 剪影（MyBodyModel 先例，避开 SMPL 授权），抠图衣物统一视觉处理后按分层槽位（上装/下装/外套/鞋 + z-order）锚点缩放叠放，支持拖拽微调；定位为「比例正确的示意图」，不承诺合身感。**v1.0 的合身表达用文字标记（最小合身标记，见 §7），不做可视化**——与 MARKET.md H3「合身判断优先、可视化为表达层」一致

> 注（2026-08-10，superseded）：纸娃娃已于 v1.0 交付并超越本条规格——叠衣为 Today 英雄区主路径（D40/D75）；底座为 photoreal catalog basewear 真人照片（D63/D64），非单色 croquis 剪影；男性已支持（AvatarBodySex / `photoreal_male_*`，D31/D34/D51），「成年女性专属公式」表述不再成立。原文保留作历史规格。

**定位修正（MARKET.md H3 判定）**：本模块的价值主张是**合身判断优先、可视化为表达层**——输出「这件在你的腰臀比上会偏紧」类可解释结论；照片试穿已商品化（Google Doppl 关停并入免费基础设施），像素写实是竞品被差评实证的失败路线（「avatar makes you skinny so it defeats the purpose」），不进入该军备赛。

验收标准：两档体型下同一衣物呈现可辨差异（锚点横向偏移 ≥5%）；肩线对齐偏差 ≤ 衣宽 5%；6 件成套渲染 ≤1s（iPhone 12+）；小样本用户测试「不觉得怪异」≥70%。

> ⚠️ **「≥5%」当前不成立（D202 实测）**：五个体型 preset 两两对比，衣物框最大差异
> **3.6%**（pear vs invertedTriangle），最小 **0.5%**（hourglass vs apple），一对都没到 5%。
> `ShapeDistinctnessCriterionTests` 已把实测钉住，几何一动就可见。
>
> **不是 bug，是两个设计立场在打架**：这条冻的是「≥5% 才叫可辨」，
> 而 `BodyMorphParams.preset` 刻意做得轻（`BodyAvatarScaler` 注释：「避免无界拉伸导致 uncanny」）。
> 更关键的是 `removingShapePreset`——**命中真体型照片时 preset warp 会被旁路**，
> 用户看到的体型差异主要来自**不同底图**，而这条量的是**衣物**。
>
> **待产品决定**：把 preset 调大到满足 5%（会改变所有人看到的画面，且 uncanny 与否只有设备上看得出来，
> 已进 `DEVICE-ACCEPTANCE.md`），还是把这条标准改成量底图而非量衣物。改哪边都要记 ADR。

**远期**：高保真试穿接生成式 try-on 商业 API（FASHN ~$0.075/图、Google Vertex virtual-try-on-001 已 GA），付费增值；**严禁**自部署非商用系开源 VTON（IDM-VTON/CatVTON/OOTDiffusion/StableVITON，均 CC BY-NC-SA/NC）。3D 体型如需求成立走 SMPL 商业授权——两条官方通道：Meshcapade（持 Max-Planck-Innovation 非独家 sublicense）或直接联系 Max-Planck-Innovation（04 报告原文写「独家」，经对抗核查修正为非独家）。

## 4. 技术架构

### 4.1 总体：端侧优先 + 无状态 AI 代理（`06-gap-3.md` 裁决）

```
┌─ iOS App（SwiftUI, min iOS 26）──────────────────┐
│ 端侧感知：Vision 抠图 / OCR / embedding           │
│ 端侧引擎：规则推荐 / FFIT / ease fit / 向量检索     │
│ 端侧 FM：availability 三态，轻任务                 │
│ 数据层：SwiftData ←→ CloudKit 私有库（零注册）     │
└──────────────┬───────────────────────────────────┘
               │ 仅 AI 请求瞬态出网（App Attest 验签）
               │ payload 不变量：无身体数据
        ┌──────▼──────────┐
        │ 无状态 AI 代理    │  Cloudflare Worker（$0-5/月）
        │ （不存任何数据）  │  或 Firebase AI Logic 托管
        └──────┬──────────┘
        ┌──────▼──────────────────────┐
        │ Provider 抽象层              │ 首发：Gemini Flash-Lite / GPT-5.4-mini
        │ （国区 provider 预留接口）    │ 国区预案：通义/豆包/DeepSeek（后置）
        └─────────────────────────────┘
```

- **不做**（MVP）：自建账号体系、全功能后端、服务端向量库（升级触发器写入 decisions.md：需要 Android/Web/社区功能时上 Supabase）
- **密钥安全**：客户端藏不住密钥 →「无后端直连」是伪命题，最低配 Worker 代理 + App Attest
- **代理状态口径修正（Codex 审计 critical）**：「无状态」限定为**不存任何用户内容**；代理必须持有**最小配额账本**（KV：attest keyId → 计数器/nonce/异常标记）——否则配额、防重放、付费权益全部不成立。**付费权益绑 StoreKit 2 originalTransactionID**（跨设备/恢复购买/家庭共享/退款撤销语义由 App Store Server API 驱动，不依赖 attest key）；免费配额以 keyId 记账 + iCloud 私有库标记双记录，缓解卸载重装重置
- **隐私叙事（诚实口径）**：「on-device first：衣橱与身体数据只在你的设备和你的 iCloud 私有库；AI 建议时相关单品图片/标签瞬态发送至模型 API、不存储」。生产必须走付费档 API（免费档数据会被用于产品改进，与叙事冲突）

### 4.4 AI 治理（威胁模型 / 输入信任边界 / prompt 治理 / 成本）

- **代理威胁模型**：每请求 App Attest assertion 校验 + 计数器防重放；**配额记账在 Worker 侧、以 attest key id 为主键**（不信任设备自报 ID，防越狱篡改/重装重置）；按 key 限频 + 全局费用熔断；attest 失败/不可用设备只降级到端侧规则层，不给云端配额
- **LLM 输入信任边界（prompt injection 防护）**：单品备注、自定义标签、OCR 文本、（v1.x）EventKit 事件标题都是**不可信输入**——一律以结构化 JSON 字段注入（不拼进指令区）、单字段长度上限、系统提示声明用户字段仅为数据；推荐理由输出过 §10.4 文案红线过滤器后才展示
- **Prompt 治理**：prompt 文本与模型 id 版本化（Worker 侧配置管理，不随 App 发版）；固定回归样本集（≥100 件标注图 → 打标断言；固定候选集 → 搭配 schema/质量断言）；回归通过才允许发布新 prompt 或切 provider——provider 抽象层的「安全切换」以此为门
- **成本可观测性**：按端点/日计量请求数与 token 花费；provider 原生 budget alert + Worker 侧日预算双告警；超限熔断 = 云端档自动降级端侧规则层并提示；设备配额异常模式（高频重置）检测

| 法务文档 | 隐私政策 + ToS/EULA（内容要点：CCPA 披露、AI payload 瞬态处理、买断/订阅条款）；无后端架构下用静态站托管政策 URL 与支持 URL；版本变更管理 |
| 隐私一致性审计 | ①LLM payload 构造层单测断言身体字段永不出现；②App 出网端点 allowlist 文档化（**rembg 服务端兜底流须纳入叙事口径或改为可选**）；③每版发布跑隐私 checklist |
| **storefront 范围（R14 已裁决）** | **仅开放 US storefront**（App Store Connect 逐区勾选，非默认全球）——与合规后置策略自洽，避免未评估市场（GDPR/PIPL 等）的法务敞口；扩区随对应市场合规完成再逐个开 |
| **遥测（R15 已裁决）** | **匿名聚合方案（TelemetryDeck 类，无 IDFA/无设备指纹）**——隐私标签从 not collected 调整为「Usage Data，未与身份关联」；红线不变（身体数据/图像永不进事件，§11.8）；采集 opt-out 可见 |

**后置预案**（进入对应市场时启动）：欧盟 = GDPR DPIA（全身照+体型画像组合）；中国 = ICP 备案（境内主体）+ 生成式 AI 属地登记 + 国产已备案模型 + AI 内容双标识 + CloudKit 云上艾珀（详见 `06-gap-1.md` 矩阵）。

## 6. 商业模式建议

调研发现一处张力并如此消解：竞品免费层「卡 100 件」被骂最多，但成本大头是 AI 调用而非存储（存储走用户 iCloud 配额，边际成本≈0）——所以：

- **免费层**：**单品数量永不设限**（差异化 + 避开口碑红线）+ 手动功能全开 + 数据导出与 iCloud 备份免费（信任底线）+ AI 配额制：
  - AI 打标前 200 件（一次性成本 ~$0.2/用户，Batch 半价后 ~$0.1）
  - 每日推送走端侧规则层（零成本不计配额）；LLM 搭配 1-2 次/日（~$0.1-0.2/月）
  - 稳态摊销 **<$0.3/月/用户**（按 `06-gap-3.md` 单价重算，原 $0.2 口径对应 100 件额度）
- **Plus 订阅**：不限 AI 打标/LLM 搭配、推送升级为 LLM 生成、fit 引擎高级、RoomPlan 地图、生成式试穿按次
- **买断档（已裁决加上）**：一次性买断解锁全部**本地功能**永久使用；**AI 云端能力走订阅**——与持续 API 成本结构对齐
- **权益矩阵（Codex 审计 + 11/14 号报告共同点名的结构风险——三档叠加易被读成多重付费墙，必须一页说清）**：

| 能力 | 免费 | 买断（一次性） | Plus 订阅 |
|------|------|--------------|-----------|
| 录入/衣橱/搭配/打卡/导出 | ✅ 不限件数 | ✅ | ✅ |
| AI 打标 | 前 200 件 | 同免费 | ✅ 不限 |
| 每日推送（规则层） | ✅ | ✅ | ✅（升级 LLM 生成） |
| LLM 搭配 | 1-2 次/日 | 同免费 | ✅ 不限 |
| 高级统计 / fit 引擎 / RoomPlan 地图 | — | ✅ 永久 | ✅ 订阅期内 |
| 生成式试穿 | — | —（v2 再议，v1 无次数包） | v2 再议 |

  规则：**v1 只有三档、无 credits**（消除三叠加）；买断用户升 Plus 按差价抵扣；单一购买入口页同屏展示三档；价格锚点 = 调研证据带（买断参考 $4.99-14.99、订阅 $30-50/年），上线前定案；100% Apple IAP、无 web 双轨计费（Style DNA 反面教材）
- 反面清单：取消/退款路径显性、无未授权扣费暗桩、免费层不投广告

## 10. 设计语言与 UX（依据 `09/10` 调研）

### 10.1 设计语言定位

**一句话**：Sézane 的温度 × SSENSE 的克制 × Notion 的效率——**衣物照片是界面唯一的色彩主角**。

- 审美参照系：以 Indyx 为代表、获目标人群正面口碑的范式（中性极简 + 自动去背统一抠图网格 + 「顾问而非机器人」的文案人格）；高端时尚电商的排版气质（SSENSE 黑白克制、NAP/Sézane 的 serif 编辑感——观察性结论）
- 明确反例：Whering 式 Gen Z 游戏化（swipe 抽卡、贴纸、高饱和）——其用户盘「skews heavily Gen Z」，且游戏化与本产品「早晨 3 分钟出门决策」的省时目标方向相反
- 视觉要素：中性暖底 + **单一低饱和 accent**（只用于主 CTA 与状态指示，HIG 对彩色内容 App 的点名建议）；sans 干活、editorial serif 点睛（约 9:1）；**严禁** AI 紫渐变、游戏化视觉、多色控件
- 拨盘（对接 frontend-checklist）：`DESIGN_VARIANCE 5-6 / MOTION_INTENSITY 3 / VISUAL_DENSITY 4-5`——推荐页画廊留白（每日「杂志封面时刻」），衣橱网格页标准密度，数据洞察页可偏密

### 10.2 Liquid Glass 采用策略（min iOS 26 = 出生在新世代）

核心心智：**两层制**——内容层（衣物摄影）+ 悬浮玻璃功能层；视觉预算全给内容层，控件层用系统默认。

- 标准 SwiftUI 组件经 Xcode 26 SDK 重编译并运行于 iOS 26 即自动获得新外观；手工项集中在四处：清理自定义 bar/sheet 背景（Apple 建议性措辞「prefer to remove」，会与系统玻璃/scroll edge effect 冲突）、自定义悬浮元素注册 `scrollEdgeEffectStyle`、搭配详情 hero 图用 `backgroundExtensionEffect`（Apple 点名的 product page 场景）、Icon Composer 分层图标（六外观变体全验收，不预裁圆角不自绘高光）
- 克制规则（Apple 官方告诫）：自定义 `glassEffect` 全 App ≤2 处（如悬浮「今日搭配」入口）且必须包进 `GlassEffectContainer`；内容层禁用玻璃；禁玻璃叠玻璃；regular/clear 变体不混用（clear 仅全屏看图/体型可视化浮层 + ~35% dimming）；bar 优先单色外观（内容鲜艳 App 的 HIG 首选项）
- 导航骨架：底部 TabView **4 tab（搭配 / 衣橱 / 日历 / 我的）**——入库不设 tab，
  它是**动作**不是目的地（本行下文「tab bar 只做导航不放动作」本就否定了入库 tab；
  D100 裁决：以实现为准，改文档）。入库入口在 Closet 的「+」，批量多选也在那里，衣橱网格页启用 `tabBarMinimizeBehavior(.onScrollDown)` 最大化照片展示；搜索用 `Tab(role:.search)`；tab bar 只做导航不放动作；卡片列表用大行高 + 同心圆角（concentric），层级靠布局分组不靠装饰边框
- 系统表面：Widget 主屏 clear/tinted 去饱和模式需 `widgetAccentable` 适配（否则衣物照片不可辨）。
  ⚠️ **实现取了另一条路（D210）**：照片不出 App 沙盒（D197 立的边界，D210 重审后维持），
  widget 上的色彩主角是每件的**调色板色点**而非缩略图。去饱和/锁屏（`accented`/`vibrant`）下
  系统会把色点全部染成同一个强调色——那时它们**在说谎**（用户会读成「今天这三件是同色系」），
  故单色渲染下**只留件名不画点**。判断住在 `TodayWidgetCopy.showsColorDots`（可测），
  WidgetKit 那侧只有一行语义映射；WidgetKit push 服务端触发每日搭配刷新；App Intents `SnippetIntent` 交互结果卡适配「今日搭配」快捷场景（⚠️ updates 页 June 2026 段属 iOS 27 SDK，min iOS 26 不可依赖）

### 10.3 关键 UX 流程

- **Onboarding 最小化**（NN/g 主张能免则免；以下数字为业界启发式而非权威标准）：个性化问题 2-3 个封顶（场合构成/所在城市/可跳过的身体维度）；注册环节天然不存在（无账号架构，§4.1）；风格测验后置为可选
- **冷启动双路径空状态**：「拍下今天这身，30 秒入库 3 件」（真实起步）/ demo 衣橱（先看效果）；录入激励用预赋进度（答完引导问题即显 20%）+ 按场合里程碑即时兑现推荐（「通勤装满 10 件，已可生成一周通勤搭配」）
- **每日 ritual**：工作日 1 条推送（默认 7:00 AM 可调），文案给结论（“Your Tuesday look is ready”）；落地单屏在拇指区完成「接受 / 换一套」决策；存放位置直接显示在推荐卡片（省一次跳转——存放位置管理与每日决策的合流点）
- **录入体验**：批量为默认路径（相册批量导入优先级 = 相机连拍）；出图管线统一去背 + 统一浅色底 + 统一边距——**影调一致是衣橱网格可扫描性的生命线**（品类 table stakes）
- **反游戏化**：不做积分/徽章/连胜；内生奖励 =「你现有衣服的新组合」+「越用越懂你」
- **通知策略**：权限延迟到首件入库/首套推荐生成后请求（价值先行，评估 provisional 静默授权）；通知类型 × 默认开关 × 频控表（每日搭配 / 日历「待处理」/ 换季与闲置提醒，分开关）；**权限被拒降级 = Widget + App 内今日卡**（每日 ritual 不因拒权静默失效）

### 10.6 产品外壳（状态/设置/数据生命周期）

- **全状态矩阵**：按页面 × {空/加载/部分成功/失败/降级/权限拒} 设计，重点四条链——入库流水线（打标中/失败/配额尽）、每日推荐（候选不足/全在洗）、天气（取不到/缓存过期）、**iCloud 未登录/存储满/同步冲突**（零注册架构的数据层单点，须显性提示「本地模式」而非静默停摆）
- **设置页 IA**：档案与身体数据（含单独同意管理）｜衣柜与单位｜通知｜订阅与买断（恢复购买）｜数据（导出/删除全部/诊断包）｜帮助与反馈｜关于（开源署名 + WeatherKit 署名 + 政策链接）
- **数据导出 spec（v1.0）**：JSON 全实体 + 原图 ZIP，设置页入口，本地生成走分享 sheet；身体维度默认不含、显式勾选才导；再导入列 v1.x
- **删除全部数据**：二次确认 → 本地 + CloudKit 私有库 + CKAsset 全清 → 完成回执；「卸载 ≠ 删除」教育文案（CCPA 删除权的产品落点）

## 11. 工程交付与运营（缺失维度审计补全）

### 11.1 Schema 演进与迁移（blocking——单向门）

CloudKit 同步的 SwiftData **只支持加法式轻量迁移**（不能删字段/改名/收紧约束），且 CloudKit 生产 schema 部署后**不可回滚**。纪律：
- v1 起启用 `VersionedSchema` + `SchemaMigrationPlan`；演进只加不删不改名，新字段**一律 optional 或带默认值**（迁移时每个属性都必须有值；D84 裁决：与 `Entities.swift` 头注释一致的 OR 口径，`id: UUID = UUID()` 这类「非 optional 但有默认」是既有基线）；新关系必须 optional 且声明 inverse；禁 `@Attribute(.unique)`
- 单向门由 `SchemaGuardTests` + golden 指纹 `Fixtures/SchemaFingerprint-v1.txt` 强制（破坏性变更硬失败；加法式需 `LOOMIES_SCHEMA_GOLDEN=record` 重录并进 diff 审查）
- CloudKit schema 上线检查单：开发环境验证 → deploy to production 前人工复核（不可逆动作）
- §2 冻结声明的例外条款以此为据；改语义/删字段仍需重新裁决

### 11.2 测试策略

- 单测清单：FFIT / ease fit / 级联语义（§2.3 转移与删除表逐条）/ 温区聚合 / 配额逻辑 / **LLM payload 隐私断言（身体字段永不出现）**
- SwiftUI 快照矩阵：Dynamic Type 全档 × 深浅色 × 无障碍双态（Reduce Transparency/Increase Contrast），接 §10.4 DoD
- 关键流 UI 测试：入库 → 推荐 → 打卡闭环；真机专项：Vision 抠图/SAM2/OCR（模拟器不可用）→ **自托管 Mac + 实体 iPhone 流水线**（Codex 审计更正：Xcode Cloud 常规测试目标是模拟器，不是真机池），覆盖最低支持机型；四条推荐正确性验收（F4）+ 双机离线竞态（§2.3）配自动化用例

### 11.3 CI/CD 与发布

- CI：Xcode Cloud 承担模拟器测试（单测 + 快照 + lint = PR 门）；Vision 系真机回归走自托管设备流水线，作为**发布门**而非 PR 门
- 发布：TestFlight 内测 → 外测两阶段 → App Store **7 天 phased release**；回滚准则 = 崩溃率 / 同步失败率阈值触发暂停放量
- 提审检查单：隐私标签与 §5 口径对账、PrivacyInfo.xcprivacy、出口加密豁免申报、年龄分级问卷、WeatherKit 署名、订阅取消路径、App Review 备注（说明身体数据用途与端侧处理）

### 11.5 可观测性与诊断

- 崩溃/性能监控裁决：**MetricKit**（MXMetricPayload/MXDiagnosticPayload + Xcode Organizer，与隐私口径兼容）；引入任何第三方 SDK 须同步重写隐私标签与叙事（联动条款）

- 设置页「导出诊断包」进 v1.0——无账号无后端架构下唯一的用户问题排查通道；Worker 侧最小日志留存期对外声明

### 11.6 离线与故障降级矩阵

- 无网可用：F3 标签/位置、F5 收藏与打卡、F6 可视化、规则层推荐（天气用缓存 + 过期标注）全可用；F1 打标排队（抠图端侧照常）、LLM 搭配不可用（显式提示非静默）
- AI 代理不可达/配额尽：降级端侧规则层 + 明确文案；重试策略有上限
- iCloud 三场景（未登录/存储满/同步冲突）：显性「本地模式」提示 + 数据留本地不丢；换机恢复流程列入一级验收用例

### 11.7 App 体积预算与模型分发

- 总包体目标 ≤200MB（初值）；SAM2 裁决建议：**Background Assets 按需下载**，未下载时降级纯 Vision 抠图（不阻塞 F1 主路径）；v1.x embedding 模型同通道；蜂窝下载征求确认

### 11.8 分析与遥测（R15 已裁决：匿名聚合）

- **方案**：TelemetryDeck 类匿名聚合 SDK（无 IDFA、无设备指纹、signal 端侧哈希化）；隐私标签申报「Usage Data，未与身份关联」，采集 opt-out 在设置页可见
- 最小事件集：激活漏斗（下载→入库 3 件→首推→首打卡）、推荐接受/换一套、打标修正率、订阅/买断转化
- 红线：身体数据与图像**永不进事件**（与 §2.2 出网不变量同级，配单测断言）
- MVP 成败指标（R1 处置的可执行化）：D30 留存、周均打卡次数、推荐采纳率——数字门槛待首批 Beta 基准数据后定

### 10.4 包容性与无障碍（硬约束，进 DoD）

- **文案红线**：禁 flattering / slimming / hide / problem area 类词汇；合身语言只评价衣服不评价身体（"这件衣长偏短" ✅ "遮住你的胯" ❌）——body-positive 是目标人群的信任底线
- 体型可视化按真实维度呈现、无「理想化」默认值；人物剪影/avatar 肤色采用 Monk 10 档量表
- 无障碍验收清单：Dynamic Type 全档（serif 标题也须缩放；最大无障碍字号下网格转堆叠布局）；对比度 WCAG AA（4.5:1 起步）；Reduce Transparency / Increase Contrast / Reduce Motion + iOS 26.1 用户侧 Clear/Tinted 偏好——全部配置双态截图验收（标准组件退化由系统自动处理，自定义元素逐项测试）；所有图标按钮带 accessibility label

### 10.5 en-US 本地化格式

- MM/DD 日期、12h AM/PM、°F 温度、英制身体维度控件（5'6" / in / lb，可切公制）——用 `MeasurementFormatter` / `Locale` 实现而非硬编码
- 尺码展示：品牌 + US 标称码（0-20 / XS-XL / Petite / Plus 副线）+ 实测维度为合身真相——与 §2.2 尺码双层分离一致（vanity sizing 脱钩策略的 UI 表达）
